## What the record decides

**Feasibility is earned by observation and declined by declaration.** Only a
completed run in the M8.2 sandbox concludes that a test is feasible. The
project's own declarations — pytest markers, a declared test command, the
declared dependency set — may decline cheaply before anything runs, with a
recorded reason. A declaration can never admit, and silence is not a claim of
hermeticity.

Seven decisions: the asymmetry above; which declarations may decline; that the
import scan does not gate; that the observing run covers the candidate tests
rather than the suite (§17's "targeted subsets only"); per-test granularity under
one per-project `pytest --collect-only` gate; every threshold as configuration
with a conservative default; and caching only the per-project gate.

## The correction that shaped it, worth not repeating

My first recommendation dropped static signals entirely, arguing that running the
tests is cheap and safe. That was calibrated on **this** repository, which is the
easy case — hermetic, ~5 minutes, no services, no credentials, no UI. §8.3
(feasibility detection and graceful degradation) names the four infeasible
classes — cloud dependencies, UI-bound behavior, live-service integration tests,
excessive runtime — and this repository exhibits none of them. Three of the four
cannot be discovered by running; you find out by hanging or by having done the
damage.

So: this repository supplies **counterexamples**, never **thresholds**. That is
why every cut-off in the record is configuration, calibrated at benchmarking.
