provider's cache key — its **name alone** breaks reuse, so no two stages can ever

not sufficient. The lever is the schema, and that is **#302**, filed as a child

## The plan Gate 1 was presented with

Four blocks, in this order. Nothing is started.

1. A run-scoped assembler that builds each request from **named content blocks**
   rather than a hand-ordered string, and orders them by a declared rank.
2. Move each stage's instructions out of the `system` message into a ranked
   block, leaving a single system message identical across every request of a
   run. Without this every request diverges at message 0 and no cross-stage
   prefix exists. **This is the load-bearing decision** — queued in
   `docs/DEFERRED.md` for approval.
3. A provider-side marker behind the client (`llm.py`), since Anthropic needs
   explicit `cache_control` breakpoints and OpenAI needs none. `cache_control`
   appears nowhere in `src/` or `tests/` today.
4. The DR #265's Acceptance requires, written as the work goes, not after.

## What the measurement actually says — read before designing

Re-run at `b7929eb`, corpus fingerprint `4b88f2b9e4aa49a0`, **unchanged** from

**The correction that matters, and it is not on the issue.** #265's comment reads
as though four stages need reordering. Three of them — `classify_coverage`,
`detect_unrequested_changes`, `recommend_tests` — are each called **exactly once
per run**, from `pipeline.py:351-359`. They have no sibling calls, so there is no
within-stage prefix to lengthen and **reordering inside those stages cannot help
them at all**. Their measured 278/403/680-token shared prefixes are cross-*run*
figures: the system prompt, which is all that two different runs share.

What they do share is **the diff**, rendered by one helper —
`coverage/prompt.py::render_diff_section` — in all three, plus `open_questions`
and `disposition`. On a 23k-token prompt that block is most of the request. So
the lever that binds here is a prefix shared **across stages**, which is #265's
"hoist repeated content across stages" candidate, not its ordering candidate.

Mapping was the open puzzle — it partitions, orders correctly already, has a
1,729-token within-run shared prefix over the 1,024 floor, and still cached on 3
of 464 calls. **Answered:** its `test_id` enum differs per batch, and the enum is
in the cache key, so every batch is a miss. That is #302, and it is no longer an
open question.

#191's technique is real and proven in the corpus (25.4% vs `main`'s 0.2% on the
same stage): `evidence/discrimination.py::_render_verdict_prompt` on branch
