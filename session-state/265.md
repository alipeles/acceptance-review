## The two findings that should shape the fix

1. **The prompt that caches well is stranded on a parked branch.** `main`'s
   discrimination prompt caches at 0.2% over 80 calls; #191's reworked one caches
   at **25.4%** over 276 calls, by putting the invariant block first and per-batch
   content last. That branch is `191-partition-discrimination`, unpushed. Look at
   what it did before designing anything new.
2. **Three of the four biggest stages cannot cache at all on this model.** Test
   recommendation, unrequested-change detection and coverage classification share
   only their system prompt between calls — 278, 403 and 680 tokens against
   OpenAI's 1,024-token minimum. Ordering cannot rescue a prefix that short;
   invariant content has to move above the variable part until the shared prefix
   clears the floor. **Those three numbers are cross-run floors** (the README says
   so, and the script marks them `?`), so confirm them per run before relying on
   them.

**Mapping is the open puzzle.** It already orders correctly and its shared prefix
is 1,729 tokens, over the minimum, and it still cached on 3 of 464 calls. Neither
ordering nor length is the constraint there. Temporal locality and byte-exactness
of the prefix are what remain. Do not assume the reordering fix covers mapping.

## The hard part of Gate 1: writing `current-task.md`

#265's Acceptance is *"cached-token fraction rises materially"* — a measurement
outcome, not a behaviour of the software. Putting that in the task file asks the
tool to derive an obligation no code can satisfy, which is exactly what the
no-dogfood-awareness rule forbids: **the issue says how we verify; the task file
says what the software must do.**

So the mandate should state the *change*, not the *result*. Something in the
shape of: invariant content precedes variable content in the named stages'
requests; the shared prefix of sibling calls in one run is at least the provider's
minimum; a stage's cache configuration is chosen by the client rather than
hardcoded per call site. The rising number stays on the issue as our verification.

Expect the decomposer to raise open questions about "materially" and about which
stages are in scope. Those are fair questions about genuinely weak wording — the
sanctioned rewrite applies.

## A design decision the session will hit

Does the lever have to change `messages` at all? It matters because that is what
re-keys the request.

- **OpenAI** (the model in use, `openai/gpt-5.4-mini`) caches automatically on
  prefix stability. There is no opt-in parameter, so the only lever is the
  content and its order — which re-keys.
- **Anthropic** requires explicit `cache_control` breakpoints, and those live
  inside the request structure too. **`cache_control` appears nowhere in `src/` or
  `tests/`.**

So a provider-agnostic answer probably belongs behind the client abstraction
rather than in each stage's prompt builder. #265's Acceptance already requires a
DR naming the lever adopted and the ones rejected — write it as you go, not after.
