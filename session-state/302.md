## What #302 is, in one paragraph

Every partitioned stage sends a **different response schema per batch**, because
`supplied_ids.constrain` embeds an enum of *that call's* ids. The provider's
prompt-cache key covers the schema, so every batch of every partitioned stage is
a cache miss by construction. #302 replaces the per-batch enum with a fixed set
of generic `slot_1 … slot_N` properties and moves the slot→id assignment into the
prompt's variable tail, where varying costs nothing.

## The measurement — do not re-derive it

`docs/experiments/265-cache-key-scope/` (script, README, committed result).
Nine live calls, `openai/gpt-5.4-mini`, both controls behaving:

| case | cached |
|---|---|
| identical repeat | 94.7% |
| identical opening, different tail, same schema | 94.8% |
| identical messages, different schema | 0.0% |
| identical messages, same schema FIELDS, different schema NAME | 0.0% |
| same schema, same enum, different tail | 94.6% |
| **same schema, enum VALUES differ** | **0.0%** |
| different opening (negative control) | 0.0% |

Two findings. The schema is in the cache key and its **name alone** breaks reuse,
so cross-stage sharing is impossible — every stage sends a different response
model. And the **enum values** break it too, so sibling calls of one stage cannot
share either. That last row is #302's whole reason for existing.

**Re-running the experiment needs a fresh nonce**, and the script defaults to
one. Its second run reported 94.9% on *every* row including both controls,
because the openings were still in the provider's cache; only the
negative-control guard stopped that being read as "caching works everywhere".

## Scope — three fields, not a rewrite of `constrain`

Only these vary **per batch**:

| stage | field |
|---|---|
| `evidence/mapping.py:183` | `test_id` |
| `requirement/obligations.py:880` | `requirement_id` |
| `requirement/linking.py:512` | `pair_id` |

Everything else keeps `constrain` untouched. `mapping.py:184`'s `obligation_ids`
is computed once before the batch loop, so every sibling embeds the identical
list; and the single-call stages (`classify`, `open_questions`, `recommendations`,
`unrequested`, `discrimination`) have no siblings at all. A per-*run* enum costs
nothing: cross-run reuse is unreachable anyway, because a different run has a
different diff and obligations, and an identical run replays from the transcript
store without reaching the provider.

## The decision the DR has to argue

#302 partially reverses **#163**, which put the enum in the schema so a foreign
id would be *unrepresentable* rather than merely rejected. Generic slots give
that up and introduce a subtler failure — **slot misalignment**, which is
well-formed and silent where an invented id announced itself by name.

Proposed mitigation: each slot echoes its `for_id`, checked against the
assignment; a mismatch is an `UnusableAnswer` and that item goes `Indeterminate`.
That restores detectability, not impossibility.

**Read #163's own text before writing the DR.** The reasoning above is
reconstructed from `supplied_ids.constrain`'s docstrings, not from #163. If #163
rests on something not accounted for here, the DR must answer it rather than
write around it. That reading was the next step when this session ended.

Counterweight worth stating in the DR: strict mode rejects `minItems` (which is
why `_Yielded` uses head+rest), but a fixed-property object requires **exactly N
answers**, so omission becomes unrepresentable. That closes **#275** — one
omitted recommendation aborting the other twelve — structurally.
