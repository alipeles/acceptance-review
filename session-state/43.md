## What #43 asks for

**Deliverable:** run a targeted subset of mapped tests in an isolated sandbox
with no network or secrets, under a time budget.

**Acceptance:** network access from within a test is blocked; exceeding the time
budget aborts cleanly and falls back to static.

## Why this comes before #42, which is the lower milestone number

`docs/DR-170-feasibility-probe.md` moved it. That record's first decision is that
**feasibility is earned by observation and declined by declaration**: nothing
static or declared may conclude a test *is* feasible, and only a completed run in
this sandbox does. Declarations may decline cheaply beforehand, but a project
that declares nothing is not thereby declaring itself hermetic.

So execution proceeds on anything the declarations did not decline, and **this
issue's two acceptance items are the only remaining rail**. A weak sandbox turns
DR-170's probe into the too-permissive failure #170 was filed to prevent — a §17
execution-safety violation the first time it runs a network-bound test on an
unfamiliar repository. That reasoning is posted as a comment on both #42 and #43.

## Two things DR-170 hands this task

- **The time budget is configuration with a conservative default**, not a
  measured value. This repository exhibits none of the four classes §8.3
  (feasibility detection and graceful degradation) names as infeasible — cloud
  dependencies, UI-bound behavior, live-service integration tests, excessive
  runtime — so it cannot calibrate one. Benchmarking does that later.
- **A declined or aborted attempt already has an outcome:** `not_attempted`
  carrying a reason, per DR-171 Decision 8. "Looked and could not" and "did not
  look" must stay distinguishable.

## The correction that shaped DR-170, and the trap it guards

My first recommendation on #170 dropped static signals entirely, arguing that
running the tests is cheap and safe. That was calibrated on **this** repository,
which is the easy case: hermetic, about five minutes, no services, no
credentials, no UI, no build step.

**This repository supplies counterexamples, never thresholds.** It can disprove
that a proposed rule always works; it cannot tell you where a rule should say no.
Any number this task needs is configuration with a conservative default.
