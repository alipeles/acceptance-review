## The lineage design — settled with the human this session

The token is a **`run_id` with a parent pointer**, not a lineage id echoed
forward. Every run prints an id; `--continue <run_id>` names the run being
continued; each ledger entry records `parent_run_id`. Lineage is the transitive
closure, derived rather than stored.

Why not the echoed-lineage-id form: one ledger file per run is already required
(three concurrent worktrees), so a unique per-run key must exist anyway. Making
the continuation token *be* that key removes the second identifier. It also kills
the ordering problem — a shared lineage id needs "the latest run in the lineage",
which needs wall-clock or a sequence number, and time must never be read back as
an input. A parent pointer never reads time at all.

**Divergence from the issue as written, agreed:** Deliverable 4 puts `carried_from`
in `RequirementDisposition`. A minted run id there would put nondeterministic
state in review state. So **`carried_from` holds the prior derivation's content
digest / request key, not the run id.** Run ids live in the ledger, the ledger
filename and stderr only; stdout stays byte-identical.

**Ruled out:** a bare `--continue` meaning "the last run in this worktree". It is
implicit lineage detection, which the issue puts out of scope, and it drags
"latest" back in. Explicit id only.

**The token authorises looking, never carrying.** Each carry is still gated on
exact requirement text match, `request_key` equality, stage-logic version, and
`source_quote` surviving as a substring. So cross-task contamination is prevented
by *identity*, independently of lineage — two mechanisms, which is what makes the
"task B against task A's ledger == empty ledger" acceptance item provable.

  `pipeline.py:275` operates on `fresh_obligations`; decompose is re-derived
  every run. Its rule today: *"A changed task invalidates everything."*
- **The pre-dedup obligation set IS persisted** — `Review.derived_obligation_map`.
- **Prior selection is NOT `latest()`** — `find_prior_review` uses git ancestry +
  commit distance and rejects a prior whose `task_source.snapshot` digest differs.
- **`Review` carries no timestamp deliberately** — wall-clock would break the
  byte-identical invariant (M0.5). That is *why* ordering came from git.
- **An uncommitted run stores under the literal `<working-tree>`**, so every Gate
  1 `check` overwrites the last. The common loop keeps no history at all.
- **Git never touches the task file.** `_read_task` (`cli.py:75`) reads the
  `--task` path; identity is a sha256 of the contents (`task_source.snapshot`).
- **The decomposer reads the WHOLE registry as context** on every call
  (deliberate, #178). That is why an identical bullet in a different task file
  can legitimately decompose differently — the reason cross-task carry is a bug,
  and the caveat on run 1 vs run 2 being a stability comparison.
- **`decompose --mode record` through `tee` writes a 0-byte log.** Run record
  bare, then rebuild the log with plain replay. Check `wc -l`.
- `gh api .../sub_issues` **paginates at 30**; sub-issues need

  `gh api repos/.../issues/<n> --jq .id`.
