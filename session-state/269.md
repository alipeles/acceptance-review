## The design, as agreed with the human

Decomposition becomes **incremental over persisted state**, not re-derived each
run. Per requirement:

| requirement | what happens |
|---|---|
| unchanged text | **no model call**; obligations carried verbatim |
| edited | one call: old text, new text, prior obligations; **ids reused where the obligation persists** |
| new | derived fresh |
| removed | dropped, and reported |

Same enforcement for linking (#144): a merge whose two obligations are unchanged
carries; a pair where either changed is re-asked.

**Anchoring bias is defeated by not asking.** The model is never shown its own
prior answer for approval — either the input didn't change and there is no call,
or it changed and there is a real diff to justify against. A stale carry-over is
caught in code: `source_quote` must be an exact substring of the NEW text, which
`_locate_quotation` already enforces.

**Ledger is the authority for prior selection** (human's call), not git ancestry.
Append-only, never compacted, one file per run (three worktrees run
concurrently), outside `.acceptance/cache/`.

**Default-to-fresh is a hard constraint, not a recommendation.** Carry-forward
consults only an explicitly continued lineage. Cross-task contamination is a new
bug in the human's words. Asserted as: *a decomposition of task B run against a
ledger containing task A is byte-identical to one run against an empty ledger.*

**No force-rederive flag.** Retracted after argument: its only function is
re-rolling, which is answer-shopping. The remedies are fix the wording (the
sanctioned rewrite, re-derives that requirement automatically) and fix the tool
(prompt change invalidates). Dogfooding forces re-derivation by clearing ledger
state, as we clear the transcript cache — a development action, not user-facing.

**Validity of a carried entry = would re-deriving it today issue the same
`request_key`?** So a minor tool update loses no work (backwards compatible by
default), and a prompt change invalidates exactly what it should. **Gap:** a code
change that alters output without changing the request (e.g. symbol enforcement
moving into post-processing) — needs an explicit stage-logic version bumped by
hand.

**Requirement identity across versions = exact text match, then align the
residue** (#209). **Confirmed by the human 2026-08-19 — settled, build on it.**
An unchanged bullet matches its predecessor deterministically and for free; only
the residue needs #209's semantic aligner, and only to tell *edited* from *new*.
Positional ids mean an INSERTED bullet
renames every later requirement in its section, which is why identity must be
content, not position. **No similarity threshold** — DR-259's "0.10 is a clean
separator" was withdrawn and #211 exists to settle it.

## Do not rediscover

- **`rerun.py` already has the carry-forward machinery, one stage too late.**
  `pipeline.py:275` operates on `fresh_obligations`; decompose is re-derived
  every run. Its rule today: *"A changed task invalidates everything."*
- **The pre-dedup obligation set IS persisted** — `Review.derived_obligation_map`.
  (I claimed otherwise mid-session and was wrong.)
- **Prior selection is NOT `latest()`** — `find_prior_review` uses git ancestry +
  commit distance and rejects a prior whose `task_source.snapshot` digest differs.
- **`Review` carries no timestamp deliberately** — wall-clock would break the
  byte-identical invariant (M0.5). That is *why* ordering came from git. Any
  ledger with time in it must sit outside review state and must never be read
  back as an input.
- **An uncommitted run stores under the literal `<working-tree>`**, so every Gate
  1 `check` overwrites the last. The common loop keeps no history at all.
- **Git never touches the task file.** `_read_task` (`cli.py:75`) reads the
  `--task` path; identity is a sha256 of the contents (`task_source.snapshot`).
- **`obligations_to_rederive` assumes ids are "a stable slug over the task
  text"** — false across seeds. It holds only because identical text replays.
- **The decomposer reads the WHOLE registry as context** on every call
  (deliberate, #178). That is why an identical bullet in a different task file
  can legitimately decompose differently — the reason cross-task carry is a bug.
- `gh api .../sub_issues` **paginates at 30** — a newly attached child will not
  appear without `--paginate`.
- Sub-issues need `-F sub_issue_id=<database id>` (integer), not `-f`, and the
  database id comes from `gh api repos/.../issues/<n> --jq .id`.
