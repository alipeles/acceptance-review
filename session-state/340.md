## What #340 does

Where a candidate test **failed** under an injected edit, the tests that went on
**passing** under that same edit are not put to the model. The tests that failed
still are, because a red test does not on its own say the named defect is what it
caught. An edit nothing failed under skips nothing, because it cannot be told
apart from an edit that changed nothing.

The human's **rule 6**: a defect whose judged pairs yield no kill has its
held-back pairs judged after all, before its rating is derived. It lives inside
`judge_pairs` because the rating is derived from what that returns and must never
see the intermediate state.

A dropped pair is recorded as `UnjudgedCause.PASSED_UNDER_EDIT`, derives no
verdict, and **raises the criterion's `unknown` count** — the human's ruling, and
the reason `support.py`'s test is written as "not `PREFILTERED`" so a cause added
later counts as unknown until someone argues otherwise.

`ExecutionSettings.route_pairs` is on by default. `decide_execution` now runs the
project's tests whenever **either** consumer wants them — routing or edit
verification — where it used to decline whenever verification was off.

## The measurement, which is the headline

| | run 1 | run 2 |
|---|---|---|
| pairs dropped | 1,526 of 15,522 | 1,885 of 20,295 |
| saving | 9.8% | 9.3% |
| cost | $2.8942 | $2.5583 |

**Why it is not 80%, in order of size:**

1. **Only a killed defect can drop anything.** 13 of 68 attempts were kills.
2. **The edit builder fails most of the time.** 39 attempts were `not_mutable`,
   and of the 37 examined in run 1, **23 (62%) returned the code unchanged** and
   9 (24%) produced Python that does not parse. #334 (sample several candidate
   edits) and #338 (a headless coding-agent injector) are the filed work.
3. **This repository is a hard case and depresses the figure.** 19 attempts came
   back `not_attempted` with reasons like *"no test went red, but 115 of 277 did
   not complete under the mutant"*. About 50 of our own tests re-enter the
   acceptance tool and start a nested pytest run; mutating the tool makes those
   hang rather than fail, so nothing is observed. **No client repository would do
   this.** The reviewing tool itself is NOT mutated — `mutated_copy` applies the
   edit only to a throwaway copy — I verified that.
4. **The large saving belongs to #335, not here.** A *verified* attempt settles
   its defect and `remaining_defect_sets` drops the whole defect from the judge,
   and that applies to a survival as much as to a kill. Routing can only ever drop
   the non-killing tests of defects that were killed.

## Still unexplained

A run where **75 candidate tests are set aside with no recorded cause** happened
twice and then not again — six clean rounds since. The bad rounds were *faster*
(112s) than the clean ones (305s), which argues against a wall-clock-budget
explanation. Queued against #184, the determinism umbrella. It is now diagnosable
if it recurs, which is what `record-set-aside-cause` is for.

The stable exclusions it did find: 5 tests failing on `UnresolvableRevisionError`
because they resolve a git revision and `copied_project` leaves history out. That
is the control check working, and it was invisible before.
