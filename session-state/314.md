## Two design calls made while building

**One request covers one test.** A request spanning several tests offers a schema
where every test crossed with every defect is expressible, so the prompt would
ask for 3 judgements while the schema invited 6, and the extras would be dropped
on the way back in — DR-164's silent filter. Per-test requests make the schema's
cross product equal the offered set.

**The response schema is `_PairVerdicts`, not `_Verdicts`.** Linking owns
`_Verdicts` and the test doubles dispatch on schema name.

## The caching fix, made and unmeasured

The stage recorded a **0.0% cached-prompt share** where mapping recorded 38.2%.
Cause was mine: the defect descriptions, identical across every call, sat inside
the per-test subject block, so the shared list was behind the unique part and no
prefix could be reused. They now sit in their own `BlockKind.DEFECTS` block ahead
of the instructions and the test.

**The win is unmeasured.** The change moves the request, so this stage's
recordings orphan and a real figure needs another `check` — which the Gate 2
suspension says not to run. Stored verdicts still carry: the carry key is built
from the system prompt and the response schema, neither of which moved.

The pipeline-wide check for misplaced shared content did not catch this, because
at fixture scale the stage has one defect and one test. Added
`test_the_defect_list_sits_in_the_shared_prefix_of_every_call`, which compares
two real calls.

# The prefilter experiment — approved, not yet started

Measure whether a cheap filter can cut the pair set before the model sees it.
**Not #314's scope**; #314's prefilter design is settled. This is new work whose
result belongs to #316, the cutover issue, or to an issue of its own.

## Why it is worth doing

Output tokens are 70% of the stage's cost and neither caching nor batching
touches them. A prefilter is the only lever that does, because removing a pair
removes its verdict. At a 1.0% kill rate there is a great deal of room.

## The human's standing instruction, 2026-08-30

**"If the filters we implement are causing us to lose real information then the
right answer may be to run multiple filters and only reject a pair if all of the
filters reject it."** Union, not intersection — a pair survives if *any* filter
keeps it. And: **embeddings are cheap next to model calls, so their cost is not a
concern.** Design to that.

## What to measure

Four candidate filters, each scored alone and in union. The question for every
one is the same: **at a threshold that excludes X% of pairs, how many of the 127
kills does it exclude?** A filter that loses a kill at any useful threshold is
rejected — that is the wrong-exclusion failure DR-312 warns about, which
re-creates #250 and #287, recommendations prescribing a test that already exists.

1. **The free baseline, measure first.** Does the test's discovery signal touch
   the defect's own file at all? `DiscoveredTest.reasons` records why a test was
   discovered and `changed_definitions` maps changed regions to symbols. No
   embeddings. If this alone excludes a large share with zero kill loss, the
   embeddings are unnecessary; if not, it is the bar they must clear.
2. **Defect description against test source**, cross-modal.
3. **Implicated code region against test source**, code to code. Possibly the
   stronger of the two, and it avoids the modality gap. `Defect.code_refs` are
   `path#hunk` labels and the change set holds those hunks' contents. A defect
   with no `code_refs` has nothing to embed and must always be kept.
4. **Union of the above**, per the human's instruction.

## The embedding-model question, unresolved

Vectors from two different models are not comparable, so both sides of any
comparison must use one model. **I believe `voyage-code-3` is the right choice**
— code-retrieval models are trained for a natural-language query against a code
document, which is filter 2's exact shape, and I believe Voyage's API takes an
`input_type` of `query` or `document` to encode that direction. **I have not
verified either claim against Voyage's current documentation and it must be
checked before building**, since the experiment depends on it. If the asymmetric
form does not hold, the fallback is to embed both sides as documents with the
same model — still valid, weaker.

`ModelClient.embed` records and replays like any other call, and
`RunConfig.embedding_model` supplies the model. Today's default is
`voyage-3.5-lite`, used by obligation linking.

## Caveats that belong in the write-up

- The 12,450 verdicts are **our own judge's answers, not ground truth**. This
  measures agreement with ourselves. For a prefilter that is the right target —
  its only job is to avoid skipping a pair the judge would have called a kill —
  but it must be said plainly.
- **One review.** Any threshold tuned on it needs holding out against #315's
  archetype labels before being trusted, exactly as DR-259 held out a fifth task
  file.
- **DR-259 is a caution, not a precedent.** Its held-out check found no threshold
  that separated cleanly. But it answered a different question — whether two
  obligations state the same requirement, a semantic-equivalence judgement —
  where this asks the much cruder "is this test even about this code". The
  difficulty does not transfer directly, and I over-weighted it earlier in the
  session.
- Follow DR-259's method: measure offline over recorded material, and read
  `docs/experiments/obligation-dedup/README.md` for the traps that analysis hit
  before repeating any of it.
