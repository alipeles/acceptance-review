## What #334 now delivers, after two decisions the human made at the gate

**The bytecode check is out of scope.** #334 originally asked for a comparison of
compiled forms before and after an edit, on the grounds that a text comparison
misses an always-true condition, a value the caller ignores and a reordering with
no effect. Measured: it catches none of those three, because all three change the
compiled form while leaving behaviour alone. It catches comment- and
formatting-only edits instead — and `mutation/verification.py`, merged that
morning for #335, already refuses those with no model call. Evidence and probe in
`docs/experiments/334-bytecode-equivalence/`. The issue body still describes the
old scope; the correcting comment is queued, not filed.

**Candidates are produced by asking again, not by sampling.** `ModelClient.complete`
hashes the whole request and reads the recorded transcript store before calling a
provider, so k identical requests return one recorded answer k times, silently.
Temperature is 0.0 by default, so identical prompts would give identical edits
anyway. The design is therefore: on a refusal, ask again and tell the model which
check refused the previous candidate. Requests differ because the prompt differs,
each candidate records and replays on its own key, and determinism holds.

The rejected alternative was putting a candidate index into the request's
`partition` field. It needs a raised temperature to produce any variety, and
`partition.py`'s docstring records that index and count were deliberately
excluded.

**Temperature above zero is a separate issue, after #334 is measured.** The human
wants the edit builder to vary. Folding it into #334 would move two variables at
once and make #334's validity measurement unattributable. Queued as a decision
with that recommendation.

## Do not mistake the ledger's derivation count for the obligation set

The ledger's `derivations[].obligations` records what each requirement
**derived**, before linking. The printed breakdown shows what **survived**
merging. Runs 1 and 2 each hold one more in the ledger than on screen, and in
both cases the gap is a single recorded merge, not a hidden obligation.

I read that gap as a hidden obligation, filed it as a blocker, and it cost a
withdrawn Gate 1 confirmation before I checked. `cli.py::_requirement_block`
iterates the requirement map's dispositions rather than the obligation set, so
it cannot suppress anything.

To compare like with like: `derivations[].obligations` **minus** the
`merge_decisions` entries whose `same_requirement` is true, against
`grep -c '^    -> ' output.log`. Detail in
`dogfood-logs/334-gate1-run3/judgement.md`.
